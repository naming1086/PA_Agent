> 记录时间：2026-09-24
> 对应代码状态：回滚后的原版装配顺序（`prompt_assembler.py` 未经缓存优化改动）
> 目的：说明 `prompt_engineering/` 里的文件如何被组装成两次 LLM 请求，以及 KV 缓存命中（`hit`）的成因与优化方向。

---

## 1. 总览

一次完整分析 = **两次 LLM 调用**，由 `pa_agent/orchestrator/two_stage.py` 驱动：

| | 第一次（Stage 1） | 第二次（Stage 2） |
|---|---|---|
| 目的 | 诊断市场处于周期频谱哪一处 | 据此选策略、定下单方式与三价 |
| 是否带策略文件 | **否** | **是**（由第一次的输出决定） |
| 是否给三价 | **否**（提示词明令禁止） | **是** |
| 请求体积 | 较小 | 较大（含第一次全部内容） |

第二次默认走 **prefix chain**，把第一次的完整对话原样重发再追加，所以第二次的 `total_prompt` 能到 13 万 token。

关键代码位置：

- 装配：`pa_agent/ai/prompt_assembler.py`
- 调度：`pa_agent/orchestrator/two_stage.py`
- 缓存统计：`pa_agent/ai/deepseek_client.py`

## 5. KV 缓存与 `hit`

### hit 是什么

DeepSeek **自动**上下文缓存：把请求内容从第一个 token 开始存，下次请求时逐 token 比对，**能连续对齐多少就复用多少**，这个数就是 `cached_tokens`。

- 读取位置：`deepseek_client.py:157`（`prompt_tokens_details.cached_tokens`）
- 打印位置：`deepseek_client.py:651`，日志形如
  `KV-cache: hit=73728 miss=59945 total_prompt=133673 hit_rate=55.2%`
- **命中部分约 0.1 倍价格，且跳过 prefill 计算** → 更便宜、更快
- 硬约束：**必须从开头连续相同**，中间任何一处不同，之后全部作废

### 缓存边界在哪

```
system     1–6    提示词大纲 + 二元决策        ← 固定，可缓存
user(S1)   7–12   市场诊断框架 + 文件16 + 内置   ← 固定，可缓存
────────────────────────────────────────────
user(S1)   13–16  K线数据表 / 特征表 / 预填     ← ❗每次都变，缓存到此为止
assistant         阶段一 JSON                  ← 变
user(S2)   18–36  阶段二全部内容                ← 变
```

**分叉点 = K线数据表**（`_build_stage1_user_prompt`，1316 行起拼表）。它之前全是静态，之后全部拿不到缓存。

因此 **hit 的理论上限 = K线数据之前所有静态文本的总量**。

### 优化杠杆

1. **换 standalone 模式**——收益最大（约 2.4x），但改变模型可见内容，需先验证输出质量。
2. **缩小必变区体积**——直接降全价部分。`feature_table`（16,377）是 Stage 1 里最大的单块可变内容，压缩列数收益最直接。
3. **稳定第 24 项顺序**（路由顺序由模型输出决定）。

| 207,797 | 27,013 | 7,218 |

`reasoning_chars=22` 那次是天然对照实验：推理几乎为空时耗时仅 **28 秒**，即
**prefill + 生成正文的固定开销 ≈ 28 秒**。

按差值推算推理速度约 **160~175 字符/秒**，验证：

```
21,770 字符推理 ÷ 165 ≈ 132 秒  +  固定 28 秒  ≈ 160 秒   （实测 155.6 秒 ✓）
```

**结论**：单次 155~207 秒中，思考生成占 **80~87%**，prefill 与正文合计仅约 28 秒。
因此**压缩 prompt 最多只能省下 28 秒中的一部分（且大部分是正文生成，不是 prefill）**，
量级上远小于推理开销。这解释了为何 1/2/3/4/5 各项对"加快"都收效甚微。

### 真正的杠杆：`reasoning_effort`
